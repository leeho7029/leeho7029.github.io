프로젝트 개요

본 프로젝트는 멀티플레이 로그 라이프사이클을 추적하여 실시간 전적 분석을 제공하는 인디 게임 Sephiria 전용 전적 분석 플랫폼입니다. 인게임 모드에서 발생하는 세션 완료(클리어, 전멸) 이벤트를 수집 서버로 비동기 전송하고, 정규화된 데이터를 PostgreSQL에 저장하여 랭킹 및 대시보드를 연동합니다.

특히, 멀티플레이 환경에서 각각의 파티원 클라이언트가 전송하는 비동기 중복 로그를 하나의 게임 세션(Run)으로 정제·병합하기 위해 런 시드, 난이도, 층 GUID, 보스 식별자 기반 Merge Key 병합 로직을 직접 고안하여 탑재했습니다. Next.js를 기반으로 웹 화면을 구현하였고 Node.js(Express) 및 Zod 페이로드 검증 파이프라인을 구축해 정해진 형식의 전적 데이터를 저장합니다.

Development Background

lightbulb 개발 배경

친구들과 Sephiria 게임을 플레이하면서 매 판 어떤 장비, 캐릭터, 공격력 빌드를 선택했는지 또 멀티플레이 보스 클리어 시 각자 얼마나 기여(Dps/피해량)했는지 비교 분석할 필요가 있었습니다. 당시 게임이 얼리액세스 단계로 공식적인 전적 히스토리를 제공하지 않아, 이를 보완하고자 플레이 수집 플러그인과 웹 전적 사이트를 제작했습니다.

report_problem 핵심 기술 해결 도전

가장 큰 난제는 멀티플레이 시 4명의 유저가 동일한 모드를 켜두었기 때문에, 보스를 깨는 순간 동일한 판의 로그 4개가 서버로 동시 전송된다는 점이었습니다.

인터넷 레이턴시로 인해 수신 시점이 모두 다르고, 호스트 여부에 따라 담긴 플레이어 정보 배열 순서와 전송 값의 미세 오차가 존재해 단순 Steam ID나 타임스탬프만으로는 같은 판(동일 런)인지 판별하여 병합하기 어려웠습니다. 이를 안정적으로 하나의 기록으로 병합하는 식별 기준이 필요했습니다.

Implementation Details

1) 멀티플레이 로그 중복 제거를 위한 Merge Key 알고리즘 고안

동일한 파티 세션에서 4명의 유저가 게임을 완료했을 때, 4개의 중복 로그가 무작위 시간차로 서버에 도달합니다. 이를 단일 판(Single Run)으로 온전히 병합하기 위해, 각 클라이언트가 개별적으로 조작할 수 없는 불변의 매치 팩터들을 조합했습니다.

실제 구현에서는 이벤트 타입, 멀티플레이 버전, 플레이어 수, 런 시드, 난이도 포인트, 층 GUID, 정규화된 보스 식별자를 조합해 merge_key를 빌드했습니다. 서버는 최초 도달한 로그로 Run 데이터를 만들고, 이후 같은 Merge Key로 도착하는 로그는 PostgreSQL ON CONFLICT 기반 UPSERT로 플레이어별 기여량과 원본 payload를 병합하도록 설계했습니다.

2) Express + Zod 스키마 검증 및 UPSERT 트랜잭션 구현

인게임 클라이언트로부터 정해진 규격 이외의 잘못된 JSON 데이터가 흘러들어와 DB 정합성 문제가 발생하는 것을 줄이기 위해 Zod를 연동해 수신 데이터를 검증했으며, 데이터 중복 삽입 가능성을 낮추는 PostgreSQL Upsert 트랜잭션 코드를 구현했습니다.

function buildMultiplayerMergeKey(payload: SephiriaEventPayload): string {
    return [
        payload.eventType,
        "multiplayer:v2",
        `players:${multiplayerPlayerCount(payload)}`,
        `seed:${clean(payload.run.currentSeed)}`,
        `hard:${clean(payload.stage.difficulty.hardModePoints)}`,
        `floor:${clean(payload.stage.floorGuid)}`,
        `boss:${canonicalBossIdentity(payload)}`
    ].join("|");
}

function pepper(): string {
    return config.privacyPepper || config.apiToken || "development-sephiria-privacy-pepper";
}

export function hashSteamId(value: unknown): string | null {
    if (typeof value !== "string" && typeof value !== "number" && typeof value !== "bigint") {
        return null;
    }

    const steamId = String(value ?? "").trim();
    if (!steamId) {
        return null;
    }

    return crypto.createHmac("sha256", pepper()).update(steamId).digest("hex");
}

export async function saveEvent(client: PoolClient, payload: SephiriaEventPayload) {
    const sentAt = parseSentAt(payload.sentAtUtc);
    const mergeKey = buildMergeKey(payload, sentAt);
    const sanitizedPayload = sanitizeSteamIds(payload);

    const run = await client.query(`
        insert into sephiria_runs (merge_key, raw_run, raw_outcome, updated_at)
        values ($1, $2::jsonb, $3::jsonb, now())
        on conflict (merge_key) do update set updated_at = now()
        returning id
    `, [mergeKey, json(payload.run), json(payload.outcome)]);

    await client.query(`
        insert into sephiria_events (run_id, event_type, sent_at_utc, merge_key, raw_payload)
        values ($1, $2, $3, $4, $5::jsonb)
    `, [run.rows[0].id, payload.eventType, sentAt, mergeKey, json(sanitizedPayload)]);

    for (const player of payload.players) {
        await client.query(`
            insert into sephiria_run_players (run_id, player_key, steam_id, raw_player, updated_at)
            values ($1, $2, $3, $4::jsonb, now())
            on conflict (run_id, player_key) do update set updated_at = now()
        `, [
            run.rows[0].id,
            buildPlayerKey(player),
            hashSteamId(player.identity.steamId),
            json(sanitizeSteamIds(player))
        ]);
    }
}

Troubleshooting

01

멀티플레이 세션 분리 및 랭킹 데이터 오염 문제

Problem

초기 수집 구조에서 Merge Key 설계가 없던 당시, 파티원 4명의 동일 판 클리어 데이터가 각각 개별 게임 세션으로 독자 기록되어 보스 랭킹 대시보드 상위권이 같은 판의 4개 기록으로 도배되는 랭킹 신뢰성 오염 현상 발생.

Solution

런 시드, 난이도 포인트, 층 GUID, 정규화된 보스 식별자, 플레이어 수를 조합한 Merge Key를 도입. 서버 단 데이터 입수 단계에서 동일 판 여부를 판정한 뒤 ON CONFLICT 기반 UPSERT 처리로 중복 로그가 랭킹에 중복 반영되지 않도록 개선.

Retrospective

인게임 수집 모드 및 API 연동 등 반복적인 Express 라우터 생성과 Next.js 서버 컴포넌트 마크업은, 사전 설계/규칙 문서를 기반으로 한 Vibe Coding(Codex 페어 프로그래밍)으로 빠르게 구현했습니다.
